# Stem: Example apps as framework probes

## Claim

Example apps are test beds for improving Dazzle. Their seeded persona jobs expose
what the DSL, runtime, renderer, and design system make easy or difficult. A
polished example is useful evidence only when the underlying job still works.

## Reconstruct

- Start from a persona's decision and the next item they need to act on. The
  first viewport has finite space; spend it on that work and its necessary
  context. Redundant chrome and a more complete inventory may obscure it.
- Trace a visible problem from URL through DSL/AppSpec to the rendered HTML
  before assigning ownership. App-specific priority belongs in the app DSL;
  repeated component behavior belongs in the renderer or HaTchi-MaXchi.
- Compare the same seeded scene before and after a change. Keep visual craft,
  job clarity, and successful interaction as separate observations.
- Promote a pattern to framework guidance only after it survives another job
  or a counterexample. A one-row preview wall is a solution for one review
  decision, not a universal layout rule.

## Not this

- Maximizing the number of cards, metrics, or catalogue components above fold.
- Treating a screenshot preference as proof that an action works or that the
  fleet has reached parity with a reference.
- Adding an HTML template or another maintained app description for agents to
  parse; the DSL and AppSpec remain the source of truth.
